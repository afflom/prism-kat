Operations and SRE · Registry operator

What does the registry keep, and what can I safely reclaim tonight?

Garbage collection is where storage bills and data loss meet. The eviction rule here is the one the spec states, and two of its promises are proved for every blob: an outstanding finalizer and a bound tag always keep a blob.

Walk it

  1. Untagged with an expired pin: the sweep reclaims it.

    gc-eviction none expired none none model answer: evict

  2. A finalizer is outstanding: kept until its controller releases it.

    gc-eviction none none outstanding none model answer: retain

  3. A session that went quiet is abandoned and its pin released.

    upload-session receiving timeout match model answer: abandoned

The decisions behind this view

GC eviction

Decision table (OMG DMN 1.5, hit policy FIRST) · grounded in UOR-Foundation/kappa-distribution

Decide whether garbage collection may evict a blob from a kappa-distribution registry, so storage is reclaimed without losing anything a tag, pin, finalizer or upload still needs.

A request is tag (whether a tag binding reaches the blob in the sweep snapshot), pin (the blob's pin: TTL 0, an unexpired TTL, an expired TTL, or no pin), finalizer (a finalizer pin and whether its controller released it), upload (whether an open upload session pin protects the content), in that order.

Promises the Lean kernel proves for every request

  • It never answers evict when finalizer is outstanding: an outstanding finalizer always blocks eviction.
  • It never answers evict when tag is bound: a tagged blob is never evicted.
  • It always answers evict when tag is none and pin is expired and finalizer is not outstanding and upload is none: an untagged blob whose pin expired is always reclaimed.

Upload session

State machine (OMG UML 2.5.1) · grounded in UOR-Foundation/kappa-distribution

Give the next state of a chunked blob upload to a kappa-distribution registry, so a client always knows whether to send, resume, retry or stop.

A request is state (the upload session's state), event (an in-order PATCH, a PATCH at the wrong offset, the closing PUT, the session TTL passing, or a cancellation), label (whether the assembled content hashes to the expected kappa-label), in that order.

Promises the Lean kernel proves for every request

  • It never answers committed when label is mismatch and state is not committed: content that does not match its label is never committed.
  • It always answers abandoned when event is timeout and state is not committed and state is not rejected: an expired session always releases its pin.

Conformance verdict

Decision table (OMG DMN 1.5, hit policy FIRST) · grounded in UOR-Foundation/kappa-distribution

Tell a platform team, from one run of the kappa-conformance binary, whether their registry is ideal, conformant or not, and what exit code CI sees.

A request is config (whether KAPPA_REGISTRY_URL and the other required variables were set), network (whether the registry under test answered), must (MUST tests that failed), should (SHOULD tests that warned), in that order.

Promises the Lean kernel proves for every request

  • It never answers ideal when must > 0: a MUST failure is never ideal.
  • It never answers conformant when must > 0: a MUST failure is never conformant.
  • It always answers conformant when config is ok and network is reachable and must <= 0 and should > 0: warnings alone never fail a reachable, configured run.
