Will my images and disks arrive whole, here and at the disconnected site?

Moving VM disks and images between clouds and sites is a chain of uploads and pulls. Prism models each step as a state machine or a policy, so an upload is always committed, rejected or abandoned, and an image is admitted the same way on every cluster.

Walk it

  1. A chunk at the wrong offset changes nothing: resume from the server's range.

    upload-session receiving gap match model answer: receiving

  2. The bytes do not hash to the label: rejected with 409, nothing half-stored.

    upload-session receiving complete mismatch model answer: rejected

  3. A signed, matching arm64 image from upstream runs on a connected cluster.

    vm-image-admission verified match arm64 upstream connected ok model answer: permit

The decisions behind this view

Upload session

State machine (OMG UML 2.5.1) · grounded in UOR-Foundation/kappa-distribution

Give the next state of a chunked blob upload to a kappa-distribution registry, so a client always knows whether to send, resume, retry or stop.

A request is state (the upload session's state), event (an in-order PATCH, a PATCH at the wrong offset, the closing PUT, the session TTL passing, or a cancellation), label (whether the assembled content hashes to the expected kappa-label), in that order.

Promises the Lean kernel proves for every request

  • It never answers committed when label is mismatch and state is not committed: content that does not match its label is never committed.
  • It always answers abandoned when event is timeout and state is not committed and state is not rejected: an expired session always releases its pin.

VM image admission

Policy decision (OASIS XACML 3.0) · grounded in ContainerCraft/kmi

Decide if a KubeVirt VM image distributed as an OCI artifact may run on a platform cluster, including an air-gapped one.

A request is signature (the Cosign signature check on the image), digest (whether the pulled bytes hash to the digest the reference names), arch (the image architecture), source (pulled from the site's own mirror or from an upstream registry), site (whether the cluster is disconnected), verifier (whether the signature verifier answered), in that order.

Promises the Lean kernel proves for every request

  • It never answers permit when signature is not verified: no unverified image ever runs.
  • It never answers permit when digest is mismatch: no image whose bytes do not match its digest ever runs.
  • It never answers permit when site is airgapped and source is upstream: an air-gapped cluster never runs an upstream pull.
  • It always answers indeterminate when verifier is error: a verifier error never becomes a permit.
